# M4G / HGS-M4：用誠實的邊際定價取代人工供給節流

> 本檔說明此版本（2026-07-31，分支 `setlevel-redesign`）新增的內容。
> 原專案說明見 [README.md](README.md)。

---

## 這個版本是什麼

RMFS（貨到人揀貨系統）中的**訂單批次與貨架派遣**決策模型。本版本新增兩個模型：

| | **M4G** | **HGS-M4** |
|---|---|---|
| 求解方式 | exact MILP（Gurobi） | 逐步貪婪 |
| 目標式 | 公尺計價、四個自我校準價格 | **完全相同** |
| 程式 | `RAWSimO.Core/Control/Defaults/OrderBatching/M4GManager.cs` | `GreedyM4GManager.cs` |
| 組態 | `Material/Instances/CoreBenchmark/small/m4g.xconf` | `hgs_m4.xconf` |
| 可擴展性 | 小規模可行，**45 車大規模跑不動** | 大規模可跑 |
| 角色 | 模型定義 + 效率上界參照 | 可部署的交付物 |

兩者共用同一個價格實作（`M4GPricing.cs`，透過 `IM4GPrices` 介面），所以比較它們可以乾淨地隔離「求解方式」這個唯一變數——這是 HADGS 之於 M1G 的同一種關係。

---

## 核心主張

> **前代模型的效率依賴人工供給節流（每站每輪限叫 1 台貨架、70 秒前瞻提前量、管線地板懲罰 20）。本版本證明這些人工常數可以被誠實的邊際定價取代。**

拿掉護欄之後，貪婪法的 pile-on 崩 46%；M4G 在完全沒有任何人工上限與手調常數的條件下，達到與前代帶著護欄相同的效率。

---

## 目標式：一份用公尺寫成的價目表

模型最小化（每項單位皆為公尺）：

```
   新叫貨架的行程距離 + 車去接貨架的距離     ← 付錢（已在途的貨架不付，沉沒成本）
 − λ  × 這一輪真的關掉的訂單行數               ← 賺錢（全額）
 − λδ × 只在估值層關掉的訂單行數               ← 賺錢（按實際兌現率折價）
 − μ  × 完成的整張訂單數                       ← 賺錢
 − ρ  × 從「正在被揀」的貨架取的件數           ← 賺錢（窗口將關，不取就得再跑一趟）
 + ρ  × 從「新叫」的貨架取的件數               ← 付錢（這件貨真的害系統多跑一趟）
```

**四個價格全部由跑動統計自我校準，目標式中沒有任何手調常數：**

| 價格 | 定義 | 語意 |
|---|---|---|
| λ | 累計行走距離 ÷ 累計關閉的訂單行數 | 平均走幾公尺才關得掉一條訂單行 |
| μ | λ × 平均每單有幾條行 | 完成一整張單值多少 |
| δ | 累計綁定行數 ÷ 累計估值行數 | 估值層說的話，多少比例真的兌現 |
| ρ | 累計貨架行程 ÷ 累計撿貨件數 | 平均每撿一件貨要走幾公尺 |

**跨規模自動適應**：從 10 車／待辦 99 張單，到 45 車／待辦 200／模型內貨架 1156 台，四個價格自動校準到合理值，**未調整任何參數**。

---

## 兩層結構

- **估值層**（`q̂`，不受站台槽位限制，看整個待辦池）：回答「這台貨架叫來能派上多少用場」。**只用於評估，不產生任何實際效果。**
- **綁定層**（`q ≤ q̂`，受槽位限制）：**只有這一層會真的發生**——在貨架上登記撿貨請求、佔用站台槽位、必要時建立子單。

每次決策從當下 backlog 重新求解，**不產生計畫、不做承諾**；被凍結的只有物理上馬上要發生的部分。

---

## 為什麼拆單會自己出現

沒有任何規則要求模型拆單。它會拆，是因為在上述價目表下拆單常常最便宜：一張單需要商品 A、B、C，站上那台貨架有 A。**現在用它把 A 清掉是免費的**（沉沒成本，甚至倒賺 ρ），剩下的 B、C 留給下一輪。

對照前代：完成一張單得 40 分，不論由 1 台或 3 台貨架服務，**拆單收益恆為 0、成本嚴格為正**，純最佳化下永不拆單——它之所以拆，是被「每站每輪只准叫 1 台」這條人工規則逼到不拆就無解。**那是可行性殘差，不是最佳化決策。**

## 主要結果

完整數據見 [`docs/2026-07-31-m4g-results.md`](docs/2026-07-31-m4g-results.md)。

⚠️ **以「處理件數」與「每件能耗」為主要指標。** 完成訂單數會系統性低估拆單模型——拆單在模擬截止時留下一批進行中的訂單，實測三個模型件數差距僅 0.15% 而完成訂單數差 2%。

### backlog 深度掃描（10 車，Fill inv70，4h，**每格 5 seeds**）

統計基礎最紮實的一組：

| backlog | 模型 | 件數 | pile-on | **每件能耗** |
|---|---|---|---|---|
| **o50** | **M4G** | 2863.0 | **2.945** | **0.8414 kJ** |
| | HGS-M4 | 2860.4 | 2.464 | 1.0025 kJ |
| | M1G | 2858.8 | 1.669 | 1.3349 kJ |
| **o100** | **M4G** | 2862.8 | **3.567** | **0.7137 kJ** |
| | HGS-M4 | 2860.2 | 3.497 | 0.8020 kJ |
| | M1G | 2398.8 | 1.479 | 1.6328 kJ |
| **o200** | **M4G** | 2864.8 | **4.194** | **0.6280 kJ** |
| | M1G（n=3） | 2524.7 | 1.556 | 1.6074 kJ |

**M4G 的件數不變（2863／2863／2865），但每件能耗隨待辦池加深單調下降 0.84 → 0.71 → 0.63、pile-on 由 2.95 升至 4.19。M1G 反向——池子越深它做得越少（2859 → 2399）。**

對 M1G 的優勢隨 backlog 擴大：每件能耗 −37.0%（o50）→ −56.3%（o100）→ −60.9%（o200）。

**與預期相反、誠實記錄**：exact 對貪婪的優勢隨 backlog **收斂**（pile-on +19.5% → +2.0%）。若此趨勢延續，「MILP 有存在理由」須限縮為「僅在待辦池較淺時成立」。

### 小案例，固定訂單檔（10 車，完全確定性，n=1）：

| 模型 | 人工節流 | pile-on | 到站次數 | 每件能耗 |
|---|---|---|---|---|
| M1G | 無 | 1.619 | 772 | 1.588 kJ |
| **M4G** | **無** | **3.483** | 348 | **0.905 kJ** |
| HGS-M3 去護欄 | 無 | 2.382 | 526 | 1.195 kJ |
| M3G | 有 | 3.576 | 330 | — |
| HGS-M3 | 有 | 4.420 | 276 | 0.788 kJ |

**大案例**（45 車，2 小時，2 seeds）：

| 模型 | 件數 | pile-on | 每件能耗 |
|---|---|---|---|
| HADGS | 6453 | 2.319 | 3.360 kJ |
| **HGS-M4** | **8190** | **3.599** | **2.366 kJ** |
| HGS-M3（手調＋護欄） | 8313 | 4.955 | 1.964 kJ |

**三個主張**

1. 同血統、同樣無節流下，正確定價使每單能耗降 **40.7%**（M4G vs M1G）
2. 誠實定價可取代人工護欄（M4G 無護欄 3.483 ≈ M3G 有護欄 3.576）——**但需要全域最佳化**
3. 同一份價目表下 exact 勝貪婪 7–32%，這是 MILP 的存在理由

**誠實的限制**：帶著調校過護欄的前代仍為全場最強。M4G 的零調參定價取得手調版增益的約 **71%**。

## 怎麼跑

```
MSBuild RAWSimOWithSolverWrapping.sln /p:Platform=x64 /p:Configuration=Release
```

x64 是唯一合法組態（Gurobi 只有 win64 版）。

```
RAWSimO.CLI\bin\x64\Release\RAWSimO.CLI.exe <layout.xlayo> <setting.xsett> <config.xconf> <輸出目錄> <seed>
```

標準基準：

```
Material\Instances\CoreBenchmark\small\small.xlayo
Material\Instances\CoreBenchmark\small\fixed_fill1350_inv70.xsett     ← 乾淨對照（確定性）
Material\Instances\CoreBenchmark\small\small_o100_mu100_4h_inv70.xsett ← Fill 模式
Material\Instances\CoreBenchmark\large\large_test-toobig-45bot.xlayo   ← 大案例
```

**消融組態**（皆由正典以單一字串取代產生）：`m4g_base`（核心機制全關）、`m4g_degen`（拿掉估值層）、`m4g_noincr`、`m4g_noepr`、`m4g_nomu`、`m4g_presentsplit`；對照組 `hgs_m3_nothrottle`（拿掉前代護欄）、`m3g_noepr`。

⚠️ 產生組態檔請用 PowerShell `[IO.File]::ReadAllText`／`WriteAllText`，**不可用 `sed`**——`sed` 會把 CRLF 改寫成 LF，使全檔被視為差異，破壞逐 byte 對照。

## 已知限制（誠實記錄）

1. **n=1**。固定訂單檔設定完全確定性，換 seed 逐位相同；要統計變異必須換訂單檔。
2. **M4G exact 在 45 車規模跑不動**，大案例僅有貪婪版本。
3. **暖機價格是內在弱點**。價格靠自我校準，校準需要資料，資料需要行動——暖機價格若與穩態差太遠，系統會鎖死在暖機裡，**兩個方向都會**：太慷慨（`DeltaFallback` 0.5）導致開場派 7–8 台車耗盡車隊；太吝嗇（拿掉 μ）導致完全不動。兩者皆已實測。
4. **槽位從未被定價**。站台槽位是最稀缺的資源（一站 6 個），但只以硬約束存在，沒有價格。前代用 `MinPartialUnits=6` 硬性擋掉「用一個槽換一點點工作」，本版本無對應機制。
5. **車輛歸還邏輯未驗證**。暖機死鎖時十台車派光未回可用池；修正後不再觸發，但不代表邏輯正確。

## 已排除的假設與已確立的平台事實

**已用實驗排除**：「在途貨架預先佔走槽位、蠶食在站貨架」不是效率差距的主因——消除八成拆單預先承諾後 pile-on 僅動 +1.1%，Fill 反而 −10.3%，且派車量上升 77%。**擋住便宜的路，模型就走貴的路。**

**平台事實**（`BotManagerPodSelection.cs`，先前未查明）：車只為身上已有撿貨請求的貨架出發；車拿著沒有請求的貨架會立刻送回儲位；撿貨請求需要訂單已佔用真實槽位。⇒ **「派車 ← 請求 ← 訂單佔槽」是引擎級鎖鏈**，真正的「虛擬槽位」需要引擎支援一種它沒有的貨架狀態。這也解開了前代 `DeferAllocationUntilProcessing` 旗標當年死鎖的原因——它在此平台上從一開始就不可能運作。
