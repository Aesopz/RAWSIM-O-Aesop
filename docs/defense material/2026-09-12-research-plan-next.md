## 2. 三組主題實驗（其餘全部砍掉）

### 第 1 組：拆單上限 N 的劑量反應 ★★★★★

`N ∈ {1, 2, 3, ∞}` × 5 seeds = 20 場 ≈ 100 分鐘（小規模）

**為什麼是最好的一組：**

1. **N=1 就是不拆單對照組** —— 曲線自己包含自己的基準線，不會有「對照組是稻草人」的質疑
2. **把貢獻從「有沒有用」升級成「要用多少」** —— 若八成效益在 N=2 就拿到，那是管理洞察不是效果宣告
3. **直接回應「成本被搬到未建模的合併牆」的批評，而且不必建模包裝站** —— N 是合併負擔的上界：每張訂單最多 N 個箱位、最多 N 次合併
4. **是真實倉儲有的作業政策旋鈕**，不是模型參數
5. 便宜

**🚨 設計陷阱（必須先定案）**

既有的 `MaxChildrenPerOrder`（`MethodConfigurationsOB.cs:931`）只存在於已放棄的
`SplitOrderManager` / `SplitPlanner`，M4G 與 M5 **各 0 次引用**。而且 `SplitPlanner.cs:21`
的註解寫的是 **"Maximal parts per epoch"** —— 每期上限。

**每期上限 ≠ 一生上限。** 每期限 2 份、跨 5 期就能拆成 10 份，那樣 N 不構成合併負擔的
上界，整個論證會垮。**必須實作跨期累計版本。**

```
M5（貪婪）   EnumerateLineMoves 時跳過會產生第 N+1 份的選項
M4G（MILP）  參數 n_o = 該訂單已產生的份數
             限制式  Σ_s y[o,s] ≤ N − n_o
```

資料層現成：`Order.CreateSplitChild`、`IsSplitParent`、demand ledger 都不用動。

### 第 2 組：包裝緩衝觀測 ★★★★（搭便車，零額外成本）

把既有的 `RAWSimO.Core/Elements/PackingBuffer.cs` 接上 M4G／M5，**只觀測不阻擋**。

- 語意已經正確：一個拆單父訂單佔一個箱位，第一次被拆時保留、合併完成時釋放
- 現況：只有 `SplitM2eICManager`（已被取代）在用，M4G／M5 各 0 次引用
- 掛載點現成：合併事件鏈已抽成 `SplitConsolidationLogger`
- 既有線索：峰值需求 **117 > Xie 假設的 78**

**與第 1 組畫在同一張圖上，就是效益與代價的損益兩平圖** —— 這會是整篇論文最有力的一張。

⚠️ 先做「只觀測」版本，看完峰值分布再決定硬限制實驗的容量水準，否則水準設錯又是一次白跑。

### 第 3 組：機器人／站台比 ★★★（補完既有曲線）

已有 6／8／10（小規模）與 45（大規模），中間是斷的且不同 layout。補完即可當適用邊界的主圖。

### 4.1 案例與求解器的分工（2026-09-12 定案）

```
小規模 + M4G（exact）     結構性主張
    消融鏈、定價機制、兩層結構、Dinkelbach、最優性證書
    理由：mipGap = 0 只有 exact 講得出口；這些主張要的是「為什麼」

大規模 + M5（greedy）     規模性主張
    vs HADGS、機器人／站台曲線、可擴展性
    理由：M4G 在大案例跑不動；這些主張要的是「撐不撐得住」

兩個規模都要              拆單本身（主貢獻）
    主貢獻只在單一規模出現，審查必問「換規模還成立嗎」
```

**🚨 必須保留橋接格。** 若每個主張只在一個 (instance, solver) 組合上測過，
規模效應與求解器效應就被綁死，無法分辨。橋接格＝兩個求解器跑在**同一個** instance 上，
把求解器效應單獨量出來。現有資料（2026-09-06 小規模配對）：

```
M5 vs M4G（同 instance）   件數 −0.04% n.s.   行數 −2.19% **
                          pile-on −8.08% *** EOR +5.48% **   快 23.0×
```

方向對我方有利 —— **M5 略遜於 M4G，所以大規模用 M5 的結果是保守下界**。
這句話要寫進實驗章，把「我用了貪婪」從弱點轉為保守性聲明。
⚠️ 速度倍率歷經 92× → 99× → 59× → 17.9× → 23.0×，引用前必查日期。

**🚨 硬規：小規模 M4G 的數字與大規模 M5 的數字永不同表。**
兩者並列時任何差異都會被讀成同時換了兩個變數。先例見
`project_m2e_sunk_first_defense`（M1G 與 HADGS 從不同表）。

### 4.2 跑批預算（實測）

```
小規模一場   約 2 分鐘        5 seeds 一臂 ≈ 10 分鐘
大規模一場   7–10 分鐘        5 seeds 一臂 ≈ 45 分鐘 ／ 3 seeds ≈ 27 分鐘
並行         三批同時跑不會搶 Gurobi 授權（2026-09-12 實測），實際吞吐約三倍
```

**先寬後深**：形狀在小規模掃（便宜、exact、可解釋），只把轉折點與端點拿到大規模確認。
不要在大規模掃格點——那是把預算燒在已知的形狀上。套用到第 1 組：

```
小規模 M4G   5 個 N 值 × 5 seeds = 25 場   ≈ 50 分鐘    掃出形狀
大規模 M5    2–3 個關鍵點 × 3 seeds        ≈ 1.5 小時   確認不翻轉
```

⚠️ 大規模冷啟動：第一次決策合法地要花 105–115 秒，不要在 90 秒就判定當機。

⚠️ 依 [[feedback-m5-must-mirror-m4g]]，N 上限必須 **M4G 與 M5 一起實作**，
否則大規模確認那一步做不了。這要寫進 spec，不能等 M4G 做完才補。

## 5. 定位與差距（寫給未來的自己）

**目前等級：紮實的碩士論文，方法論紀律高於平均。**

**要往期刊走，缺的是這三件（依重要性）：**

1. **合併成本沒有被建模** —— 這不是限制，是效度威脅。量了效益、沒量代價。第 1、2 組就是補這個
2. **單一 instance family** —— 一個 layout 家族、一個訂單產生器、一套物理模型，外部效度薄
3. **沒有前瞻型基準** —— 沒有與 rolling-horizon／ADP／bid-price 類方法比較。`paper/adelman2007.pdf`
   在手上但沒用上

**最大的敘事風險：**

對外部基準 M1G，**定價的貢獻實測為 −1.92% n.s.，拆單才是 −34.00% (t=−43.1)**。
動態 vs 固定的 12–14% 是**模型內部**的比較（自己把旋鈕關掉），不是對競爭方法的優勢。

⟹ **主敘事必須以拆單為主體、定價為使能器**，不能倒過來。標題已經是對的
（考慮訂單拆分…），但投影片與實驗投入長期偏向定價，這個錯配要修正。

**最強的可用敘事線：**

> 拆單帶來增益 → 但裸拆會崩潰（啟發式拆單 pile-on 暴跌）→ 因此需要聯合最佳化
> 與一個自我校準的匯率才能實現 → 而它把成本搬到下游合併 → 這是那個成本的量級，
> 以及用 N 把它框住的方法。

這條線用得到全部既有資產，而且把最弱的一環（定價的外部證據）放在使能器的位置，
而不是主張的位置。
