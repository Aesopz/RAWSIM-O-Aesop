## 1. 一段話定位

M1e/M2e 是拆單模型家族的「精確版終點」：把 SplitM1G（M1/M2）留給求解後貪婪法的
**「哪一件貨從哪一個 pod 拿」**這個決策，收進 MILP 本體——決策變數從三維
`q[SKU,單,站]` 升成四維 **`q[SKU,單,pod,站]`**，同時把獎勵從「每出一件 −40」
改回「每**完成**一張單 −40」。結果是：求解器輸出的解**就是**最終揀貨工單，
不再需要貪婪分配、不再需要反悔機制；而且修掉了 per-unit 獎勵「偏好少張大單」
的已知偏差（small 實測：M1e 完成 649 單 ≈ M0 的 654，但 pile-on 高 13%）。

一個比喻：M0 是「整箱訂單配給一個櫃檯」；M1/M2 允許「拆箱，各件分頭辦理，
但去哪個櫃檯自己想辦法湊材料」；M1e/M2e 是「拆箱，而且**每一件都指定好
從哪個倉格取料、在哪個櫃檯辦理**」——整張作業單一次開齊，執行端零裁量。

## 2. 每次決策吃進什麼（快照輸入）

每次 `DecideAboutPendingOrders` 觸發，`InitializeSplitExact` 抓一份當下快照
（與 SplitM1G 的 `InitializeSplit` 同構,全部以**殘量**計）：

| 符號 | 內容 | 白話 |
|---|---|---|
| $\mathcal{S}$, $C_s$ | 有空槽的站與其剩餘槽位 | 「哪些櫃檯還有空窗、各空幾格」 |
| $\mathcal{O}$, $r_{o,i}$ | 過濾後的 backlog 與殘餘需求 | 「還有哪些單、各還欠哪些貨幾件」——欠量=原需求−已被 child 認領（跨期帳本） |
| $\mathcal{P}^b$ / $\mathcal{P}^a$ | 在途 pod / 儲位候選 pod | 「已經在路上的貨架（不可反悔）/ 可以新派車去搬的貨架」 |
| $\mathcal{P}_i$, $e_{p,i}$ | 每個 SKU 的載貨 pod 倒排索引與可用量 | 「這種貨誰身上有、各有幾件（已扣掉別人預訂的）」 |
| $\mathcal{R}^a$ | 空閒機器人 | 「還有幾台車可派」 |

進場過濾（模型外的前處理）：M1e 要求訂單**所有**殘餘 SKU 都有貨才進模型
（否則本期注定湊不齊，何必進來）；M2e 只要**任一** SKU 有貨就進（能出一件是一件）。

## 3. 變數（決策的語彙）

| 變數 | 型別 | 白話 |
|---|---|---|
| $q_{i,o,p,s}$ | 整數 ≥0 | **主角**：「訂單 $o$ 要的 SKU $i$，從 pod $p$ 取幾件、送到站 $s$ 揀」——四個問題一個變數答完 |
| $x_{p,s}$ | 0/1 | 「pod $p$ 這趟去站 $s$」 |
| $v_{r,p}$ | 0/1 | 「機器人 $r$ 負責搬 pod $p$」 |
| $y_{o,s}$ | 0/1 | 「訂單 $o$ 在站 $s$ 佔一個槽位（=會生一張 child 單）」 |
| $z^{full}_o$（M1e）/ $z^{done}_o$（M2e） | 0/1 | 「這張單本期**完全**搞定」——獎勵發放的依據 |
| $u_s$ | 整數 0..$C_s$ | 「站 $s$ 本期空著沒用的槽位數」——要被重罰的量 |

對比 SplitM1G：$\delta_{o,p,s}$（dops）與 shi12 **整組消失**——那是給貪婪法
做比對線索用的輔助變數,pod 歸屬進了模型後沒有存在理由。

## 4. 目標函數（在最佳化什麼）

$$
\min\;
\underbrace{w_1\Big(\sum_{p\in\mathcal{P}^a,\,s} c_{p,s}\,x_{p,s} + \sum_{r\in\mathcal{R}^a,\,p\in\mathcal{P}^a} c_{r,p}\,v_{r,p}\Big)}_{\text{①跑腿成本}}
\;+\;
\underbrace{w_2 \sum_{o} z_o}_{\text{②完成獎勵}}
\;+\;
\underbrace{w_3 \sum_{s} u_s}_{\text{③空槽重罰}}
$$

$w_1=1,\; w_2=-40,\; w_3=1000$。白話的優先序（由權重量級決定）：

1. **先把櫃檯填滿**（③每空一格罰 1000,壓倒一切）——這是「讓站台保持 busy」的機制化。
2. **再多完成整張單**（②每完成一張賺 40）——注意是「完成」不是「出件」。
   這就是修 confound 的地方：SplitM1G 的 per-unit 獎勵下,出 5 件大單的一半
   和出 5 張 1 件小單等值,solver 於是偏好少張大單、orders-handled 指標難看；
   M1e/M2e 只有「整張搞定」才計分,與 M0 的獎勵哲學重新對齊,消融比較才乾淨。
3. **最後才省路程**（①係數最小）——同樣填滿、同樣完成數的方案裡,挑近的
   pod、近的機器人。

## 5. 約束逐條拆解（含「沒有它會怎樣」）

這一節是本文件的核心。每條給：數學式 → 白話 → **反事實**（拿掉它系統會怎麼壞）。
其中兩條的反事實不是想像——是 Task 6 煙霧測試**真實崩潰過**的案例。

### 5.1 elink1：庫存守恆（跨訂單聚合）★煙霧實證 bug #1

$$\sum_{o} q_{i,o,p,s} \;\le\; e_{p,i}\cdot x_{p,s} \qquad \forall\, i,\; p\in\mathcal{P}_i,\; s$$

**白話**:「所有訂單加起來，從 pod $p$ 拿走的 SKU $i$ 總量，不能超過 $p$
實際帶著的量；而且 $p$ 沒被派去站 $s$（$x=0$）的話一件都不能拿。」

**沒有它會怎樣（實證）**:spec 初版寫成逐訂單上界
$q_{i,o,p,s} \le e_{p,i}\,x_{p,s}$（每張單**各自** ≤ 庫存）——兩張單就能
**各自**把同一 pod 的同一 SKU 拿好拿滿,加總超過實體庫存。煙霧第一次跑,
在 `JustRegisterItem`（向 pod 預訂實體件）當場炸出
`Cannot reserve an item for picking, if there is none left of the kind!`。
教訓:**「每個人都不超量」≠「大家加起來不超量」**——聚合守恆必須顯式寫。

### 5.2 elink3：有量必佔槽 ★煙霧實證 bug #2

$$\sum_{p} q_{i,o,p,s} \;\le\; r_{o,i}\cdot y_{o,s} \qquad \forall\, o,\; i\in\mathcal{I}_o,\; s$$

**白話**:「訂單 $o$ 在站 $s$ 只要有任何出貨量,就必須把 $y_{o,s}$ 打開
——也就是**誠實承認它佔了這站一個槽位**;而且該站出的量不能超過殘量。」

**沒有它會怎樣（實證）**:spec 初版漏了這條（只有反方向的 elink2）。solver
發現一個漏洞:讓 $q>0$ 賺完成獎勵、卻把 $y$ 全壓 0——槽位守恆 eshi4 看到的
是「零佔用」,於是放行遠超容量的分配。decoder 照 $q$ 開 child 去配站,
第一個決策就想塞 70 張單進 12 個槽,`RegisterOrder` 炸出
`Cannot reserve more capacity than this station has!`（超收 ~6 倍）。
教訓:SplitM1G 的 slink1 一條式子**身兼二職**（限量+佔槽）,四維化拆開重寫時
只搬了限量、丟了佔槽——**重構聚合約束時,要逐一清點原式暗中承擔的每個語意**。

### 5.3 elink2：佔槽必有量（elink3 的反向）

$$y_{o,s} \;\le\; \sum_{i}\sum_{p} q_{i,o,p,s} \qquad \forall\, o,\, s$$

**白話**:「反過來,沒有實際出貨就不准佔槽」——禁止空頭 child。
elink2+elink3 合起來把 $y$ 和 $q$ 雙向鎖死:**佔槽 ⟺ 有量**。

**沒有它會怎樣**:solver 可以開一堆 $y=1$ 的空 child 去「假裝填滿」eshi4、
躲掉 $u_s$ 的 1000 重罰——站台帳面滿載、實際沒貨可揀,吞吐歸零。

### 5.4 eshi4：槽位守恆

$$\sum_{o} y_{o,s} \;=\; C_s - u_s \qquad \forall\, s$$

**白話**:「站 $s$ 本期收的 child 數 + 認列的空槽數 = 它的空槽總數。」
等式（非 ≤）配合 $u_s$ 的重罰,逼 solver 能填就填。

### 5.5 eM1 / eM2 / eM2done：拆單模式的分水嶺

$$
\text{M1e:}\quad \sum_{s}\sum_{p} q_{i,o,p,s} = r_{o,i}\cdot z^{full}_o \qquad \forall\, o,\, i
$$

**白話**:「要嘛這張單**每一個** SKU 的殘量都在本期出清（$z=1$,可以跨站跨
pod 湊）,要嘛一件都不動（$z=0$）」——本期全有全無,不留半吊子。

$$
\text{M2e:}\quad \sum_{s}\sum_{p} q_{i,o,p,s} \le r_{o,i}
\quad\text{且}\quad
\sum_{s}\sum_{p} q_{i,o,p,s} \ge r_{o,i}\cdot z^{done}_o \qquad \forall\, o,\, i
$$

**白話**:上式「出多少都行,不超過欠量」（欠的留 backlog 下期再說=跨期）;
下式「想領完成獎勵（$z^{done}=1$）?那**每個** SKU 都得出清才算」。
≤ 和 ≥ 夾出的語意:**部分進度合法,但獎勵只發給完賽者**。

**沒有 eM2done 會怎樣**:M2e 就沒有任何機制分辨「完成一張單」和「東出一件
西出一件」,獎勵無處掛,退回 per-unit 的偏差世界。

**一個誠實的語意註腳（論文要寫）**:$z^{done}_o=1$ 的精確意思是「$o$ 的所有
**模型可見**殘餘 SKU 本期出清」。M2e 允許某 SKU 全倉缺貨的訂單進場,該 SKU
不建 $q$ 變數、也不在 eM2done 的 $\forall i$ 範圍內——所以 $z^{done}=1$ 不
保證「訂單字面上完成」。這只影響目標函數的計分,不影響任何實體帳（decoder
不讀 $z$,母單完成與 KPI 一律由殘量帳本把關）;偏差方向（獎勵推進可推進的單）
也算合意。但寫論文時 $z^{done}$ 的定義要照實寫。

### 5.6 eshi13′：新派的 pod 不准白跑

$$x_{p,s} \;\le\; \sum_{o}\sum_{i} q_{i,o,p,s} \qquad \forall\, p\in\mathcal{P}^a,\, s$$

**白話**:「特地派車去搬的新 pod（$\mathcal{P}^a$）,到站後至少要被拿走一件,
否則不准派」。SplitM1G 靠 $\delta$（dops）近似這件事,但 $\delta$ 只跟
$y/x$ 掛鉤、從未連到真實消耗量,所以那邊「選了卻沒用」的情況真的會發生,
才需要求解後的反悔機制。這裡直接對 $q$ 求和,**是精確保證不是近似**——
反悔機制因此整段消失。

### 5.7 骨架約束（自 M1G 逐字繼承,語意不變）

| 式子 | 白話 |
|---|---|
| eshi6: $\sum_s x_{p,s} \le 1$ | 一個 pod 一趟只去一站 |
| eshi7/eshi11: $x_{p,s}=1,\ v_{b(p),p}=1\ \ \forall p\in\mathcal{P}^b_s$ | 已在路上的 pod 和它的司機,本期不准反悔改派 |
| eshi8: $\sum_s x_{p,s} \le \sum_r v_{r,p}$ | 想用 pod 得先有機器人扛 |
| eshi9/eshi10: $\sum_r v_{r,p} \le 1,\ \sum_p v_{r,p} \le 1$ | 一車一架、一架一車 |

## 6. M1e vs M2e：同一副骨架,一組開關

兩者共用全部約束,只差「拆單模式分水嶺」那組（§5.5）與完成旗標的名字。
config 上就是 `SplitM1GExactConfiguration.CrossTime` 一個布林:

| | M1e（CrossTime=false） | M2e（CrossTime=true） |
|---|---|---|
| 跨站 | ✅ | ✅ |
| 跨期（部分滿足留殘量） | ❌ 本期全有全無 | ✅ |
| 完成旗標 | $z^{full}$（=1 才准動這張單） | $z^{done}$（=1 才計獎勵,部分進度自由） |
| 進場門檻 | 所有殘餘 SKU 有貨 | 任一殘餘 SKU 有貨 |
| 直覺 | 「湊得齊才動手,動手就做完」 | 「能出一件是一件,做完才計功」 |
| 已知代價 | 挑單保守,可能放著可部分推進的單不動 | consolidation 尾巴（跨期 child 等最後一塊拼圖） |

## 7. 求解後處理：從「第二次決策」退化成「抄寫」

SplitM1G 求解後要跑三段:貪婪 Ziops 逐件猜 pod → 反悔撤銷沒用到的 pod →
記帳。M1e/M2e 的解已含 pod 維度,管線只剩「格式轉換」:

```
q[i,o,p,s] 的解
  │ 按 (o,s) 把 pod 維度加總（SplitM1GExactAggregator——純函式,4 個單元測試）
  ▼
每站 parts = (s, {SKU: 件數})
  │ SplitMilpDecoder.Decode（Spec 2 原件不動,防禦性驗證:超量/未知SKU/M1沒湊滿 → 丟例外）
  ▼
單站全數且沒拆過 → 快路徑:母單直接配站（行為 = M0,零開銷）
否則 → 每站 CreateSplitChild（兩段式原子扣殘量帳本,防跨期重複認領）
  │
  ▼
Ziops 直接照 q 逐筆寫入（「哪張單哪個 SKU 從哪個 pod 揀幾件」——不是算出來的,是抄下來的）
機器人認領（v=1 且 r∈Ra → ClaimPod）、母單記帳（首拆設 TimeStampSubmit,認領完退 backlog）
```

**為什麼敢說不需要反悔**:elink1 保證抄下來的量必有貨（§5.1）,eshi13′ 保證
新 pod 必被用到（§5.6）,elink2/3+eshi4 保證槽位帳一致（§5.2-5.4)——反悔機制
要修補的三種「解與現實的落差」在模型層就不存在了。

## 8. 代價與實測：多一個維度買了什麼、花了什麼

**買到**:pod 歸屬最優化（不再是貪婪近似）、反悔機制刪除、per-order 獎勵可
掛載、以及乾淨的落地語意（解=工單）。small seed0/7200s 實測:

| | M0 | SplitM1G-M1 | SplitM1G-M2 | **M1e** | **M2e** |
|---|---|---|---|---|---|
| OrdersHandled | 654 | 565 | 552 | **649** | **643** |
| OrderPileOn | 1.735 | 1.744 | 1.488 | **1.961** | **1.931** |
| OrdersLate | 2 | 6 | 8 | **2** | **5** |

M1e 訂單數幾乎追平 M0、pile-on 高 13%、逾期回到 M0 水準——confound 修復的實證。

**花費**:變數數乘上 pod 維度（small 平均每決策 ~87 單×~90 pod 規模下,q 從
數百變數千~上萬）。實測求解時間:**中位 0.045s、p95 0.096s、max 4.26s**
（697 次決策全部解到最優）。中位數無感,但 **max 4.26s 的尖峰是規模警訊**——
45-bot 大陣地（推估 q ~10⁵ 量級）的 tail 風險,就是 PVGS heuristic 討論稿
（`docs/2026-07-07-pvgs-fast-heuristic-discussion.md`）存在的理由。

## 9. 給口試的三句總結

1. **做了什麼**:把拆單決策的最後一塊裁量權（件→pod 歸屬）從求解後貪婪法收進
   MILP,變數升四維,獎勵改 per-order 完成。
2. **為什麼對**:兩個煙霧實證的反例（庫存超提、槽位超收）證明聚合模型的鬆散
   不是理論潔癖——精確化之後,解本身就是可執行工單,反悔機制整段刪除。
3. **代價與出路**:求解時間中位數無感但尾巴翹起,大規模需要 heuristic 對應
   （PVGS,對應關係=HADGS 之於 M1G),這是論文方法階梯的下一格。
