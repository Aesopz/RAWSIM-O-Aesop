# M4G 完成獎勵缺陷、HGS-M5 啟發式、以及拆單的可解性效益

2026-08-04。這份文件記錄一輪調查的完整經過與結論，包含**兩個被推翻的中間結論**——留著它們是因為推翻的過程本身就是方法論素材。

案例除另有註明外一律為：`small_10bot.xlayo` / `small_o100_mu100_2h_inv70.xsett`（2 小時、10 台車、2 個揀貨站、庫存 70%）/ seed 0。

---

## 1. 核心缺陷：M4G 為它沒完成的訂單付完成獎金

### 症狀

同一個 top-K=10 策略下，貪婪啟發式 HGS-M5 在完成訂單數上贏過精確求解的 M4G（599 vs 569）。這違反直覺——兩者共用同一個目標式，貪婪建的解落在 M4G 的可行域內。

### 診斷

決策日誌顯示搬運工作量幾乎一模一樣，差別只在完成認定：

| 全場總計 | M4G K=10 | HGS-M5 K=10 |
|---|---|---|
| 關掉的行 | 935 | 932 |
| 綁定件數 | 1446 | 1447 |
| 派車 | 97 | 105 |
| **模型宣稱完成的訂單** | **826** | **610** |
| **實際完成的訂單** | **569** | **599** |

全場只存在過 672 張訂單，M4G 卻累計 826 次 `z=1` 事件——至少 154 次是同一張訂單被重複認定完成。

### 根因

`BuildSnapshot` 收訂單的條件是 `.Any`（只要有**一條**行有貨就收）：

```csharp
HashSet<Order> candidates = new HashSet<Order>(_pendingOrders.Where(o =>
    o.RemainingPositions.Any(p => Instance.StockInfo.GetActualStock(p.Key) >= 1)));
```

但強制「完成」的限制式 B5/B7 —— 以及 `ch`/`Chat` 符號本身 —— 只走通過 PiSKU 過濾的行：

```csharp
foreach (var sku in snap.Residuals[order].Where(p => snap.PiSKU.ContainsKey(p.Key)))
{
    wrapper.AddConstr(Σ skuDraws >= sku.Value * bin[cName], "B5");
    wrapper.AddConstr(bin[cName] >= bin["z_" + order.ID], "B7");
}
```

一條「這次決策無任何貨架可供」的殘量行**沒有 `c` 變數、不受任何限制式約束**，求解器仍可把 `z_o` 設為 1。而目標式對 `z_o` 付 −μ。

**M4G 因此被積極誘導去挑那些「帳面上能完成、實際上服務不到」的訂單組合。** 精確求解器會系統性地榨取這個誤差，貪婪只會偶然撞到——這就是「精確輸給貪婪」的機制。

### 為什麼 top-K 讓它爆發

| 配置 | 宣稱完成 | 實際完成 | 灌水 |
|---|---|---|---|
| K=0 | 619 | 608 | 1.8% |
| K=10 | 826 | 569 | **45.2%** |

截掉候選貨架 ⟹ `PiSKU` 覆蓋的 SKU 變少 ⟹ 更多訂單有無貨可供的行 ⟹ 免費 `z=1` 的機會暴增。

**M4G + top-K 被打了兩次**：候選集變小（真實成本）加上漏洞被撐開（假成本）。HGS-M5 沒有漏洞，只付第一項。

### 這個洞曾被發現，但補丁掛錯地方

`ForbidSplitting` 路徑裡早就有同一個補丁：

```csharp
// (V8g) A pending order can have a residual SKU with zero PiSKU coverage this
// decision ... nothing above would otherwise stop the solver setting zhat=1 "for free"
if (!fullyCoverable) wrapper.AddConstr(bin["zh_" + order.ID] == 0, "V8g");
```

但它被關在 `if (_m4gConfig.ForbidSplitting)` 裡面，正典 M4G 完全沒有保護。

### 修法

`M4GConfiguration.HonestCompletionReward`（**預設 true = 修好的行為**；設 false 可重現 2026-08-04 之前的結果）。新增無條件的 `V4g`：

```
若 order 的殘量中有任何一行這次決策無貨可供：zh_o = 0
（z_o 透過既有的 B6z: z ≤ zh 一併歸零）
```

**拆單不受影響**——部分取貨照樣合法，只是不能為此領完成獎金。這本來就是 μ 的語意（公尺／**完成**一張訂單）。

### 修正後（small 7200，seed 0）

| arm | 件數 | 完成訂單 | 宣稱完成 | kJ/訂單 | kJ/件 | pile-on | 周轉 | 積壓 | 牆鐘 |
|---|---|---|---|---|---|---|---|---|---|
| M4G K=0 修正前 | 1430 | 608 | 619 | 1.1626 | 0.4943 | 5.903 | 1201 | 74 | 526.8 |
| **M4G K=0 修正後** | 1430 | 603 | 612 | **1.1439** | **0.4823** | 6.153 | 1151 | 74 | 480.1 |
| M4G K=10 修正前 | 1431 | 569 | 826 | 1.2001 | 0.4772 | 5.927 | 1314 | 103 | 130.2 |
| M4G K=10 修正後 | 1429 | 603 | 612 | 1.1629 | 0.4907 | 6.347 | 1095 | 72 | 100.9 |
| HGS-M5 K=10 | 1430 | 599 | 610 | 1.1563 | 0.4844 | 6.112 | 1273 | 66 | **5.2** |

宣稱完成 826 → 612（與實際 603 差 1.5%），積壓 103 → 72，完成訂單 569 → 603。

### 稽核範圍（其餘皆正確）

| 項目 | 判定 |
|---|---|
| λ 的行關閉獎勵 | ✓ `Chat` 符號本身就只為 PiSKU 覆蓋的行建立 |
| μ 的價格校準 | ✓ `RegisterCompletedOrders` 餵的是 `snap.Residuals[order].All(...)`，不過濾 |
| δ 的校準 | ✓ 用行數比值，行的計數誠實 |
| HGS-M5 的完成認定 | ✓ `coversAll = partUnits == residUnits`，殘量全額 |
| `StatOverallOrdersHandled` | ✓ 只算母單（569 < 已下單 672） |

**價格校準一直是誠實的，灌水只發生在目標式的誘因上。**

## 2. 被推翻的中間結論（保留為方法論素材）

### 2.1 「截斷對兩個模型都是好策略」——錯

修正前量到 M4G 加 top-K 從 kJ/件 0.4943 改善到 0.4772，我據此宣稱截斷是對兩個模型都成立的獨立發現。**那個改善完全是 bug 造出來的。**

修正後：

```
M4G K=0  ：kJ/件 0.4823，kJ/訂單 1.1439
M4G K=10 ：kJ/件 0.4907，kJ/訂單 1.1629   ← 更差
```

**截斷對 M4G 有害，對 HGS-M5 有益**（M5 未受修正影響，K=0 的 0.4996 → K=10 的 0.4844 仍成立）——因為 M5 沒有漏洞可被撐開，只享受「少評估邊際派車」的正面效果。

### 2.2 「kJ/件是有效的效率指標」——不足

`items handled` 在這個案例是**飽和**的（所有 arm 都是 1429~1431），不會動，所以擋不住任何東西。真正在動的自由變數是**完成訂單數**。

用 kJ/件 會產生假性增長：少完成訂單、把單堆成 WIP，比值就漂亮。實例：

```
M4G K=10 修正前：kJ/件 0.4943 → 0.4772（看起來 −3.5%）
                  kJ/訂單 1.1626 → 1.2001（實際 +3.2%）
```

**報告協定**：能耗一律三個一起報——「完成訂單數、kJ/訂單、期末積壓」。只有在完成訂單數不劣化時，kJ/件 才有意義。

## 3. HGS-M5：M4G 的行級邊際貪婪對應物

`RAWSimO.Core/Control/Defaults/OrderBatching/GreedyM5Manager.cs`
規格：`docs/superpowers/specs/2026-08-03-hgs-m5-marginal-line-greedy-design.md`

HGS-M4 問「這期我能**完整完成**哪張單」，湊不滿就跳過。HGS-M5 問「現在最好的**邊際動作**是什麼」，兩種動作：

- **draw-line**：把某訂單某行的**全部殘量**從站台既有庫存取走。`Δ = −λ (−μ 若為該單最後一條開放行) ± ρ·件數 − ε·件數`
- **dispatch**：派一台 Pa 貨架，計價為淨額（扣掉它立即解鎖的 draw-line 價值）

接受最負的動作，沒有負的就停。槽位與空閒車是**硬限制、不定價**，與 M4G 的 B3 一致。

### 同質性對齊

目標式與 M4G **逐項相同，包含估值層**：綁定的行earn −λ，只有估值層能關的行 earn −λδ（μ 對訂單同理）。`ValuationSweep` 重現該項，`RegisterDecision` 餵入相同的 綁定/估值 比值。

對齊的直接證據：**δ 自己收斂到同一個值**（M4G 0.166 vs M5 0.164，五 seed 0.153~0.173），對照未對齊的 HGS-M4 是 0.946。

對齊使 M5 抓到的 M4G 能耗增益從 64.2% 升到 **96.2%**。

### 仍存在的差異（屬「貪婪」本身，無法消除）

1. 訂單掃描順序（`Timestay` → `DueTime`）。貪婪必須有先後，MILP 沒有。
2. **一行不能跨站台湊滿**（同站台跨貨架可以）。
   > 更正：spec §2.3 寫「一行不能跨**貨架**湊滿」是錯的，同站台內可以。正確的限制是不能跨**站台**。
3. 估值層是貪婪掃的，M4G 是最佳化的，所以 M5 的估值信用略低估。

### 拆單能力

| | 跨站 | 跨期 |
|---|---|---|
| 訂單拆成多行 | M4G ✓ / M5 ✓ | M4G ✓ / M5 ✓ |
| 單一行再拆 | M4G ✓ / **M5 ✗** | M4G ✓ / **M5 ✗** |

實測證據（al_m5_s0，2 站台）：197 張拆單母單中 **29 張有 3 個以上子單**——2 站台一期最多生 2 個子單，故必然跨期。

### 效能優化（三輪，每輪逐位一致）

| 版本 | 決策時間 | 整場牆鐘 |
|---|---|---|
| 對齊後原版 | 50.0 s | 52.9 s |
| ① `CloneForTrial` 寫時複製 | 45.8 s | — |
| ② `DrawOrder` 記憶化 + 去 LINQ | 18.7 s | 22.4 s |
| ③ 合併兩次貨架走訪 + tier 快取 | **17.0 s** | **20.1 s** |

**猜錯兩次值得記錄**：先賭深拷貝是主因，只快 8.4%。真兇是 `DrawOrder` 的 `OrderBy().ThenBy().ToList()`——被 `RhoForDraw` 和 `UnitsFromNewPods` 各叫一次，**每個候選動作兩次 LINQ 排序**，一次決策約 30 萬次。

## 4. 件級 vs 行級拆單原子：件級一文不值

`M4GConfiguration.LineAtomicSplitting`（gated，預設 false）把拆單原子從**件**收緊到**行**——即 HGS-M5 的解空間，但用精確求解。

| 指標 | M4G | M4G-lineatom | HGS-M5 |
|---|---|---|---|
| 件數 | 1430 | 1430 | 1430 |
| kJ/件 | 0.4943 | 0.4913 | 0.4996 |
| 牆鐘 | 526.8 s | 499.6 s | 52.9 s |

差 0.003 kJ/件，而 M4G 五 seed 的全距是 0.041——**純噪音**。結論：**把原子從件收緊到行，量不到任何代價**。

意義：HGS-M5 的解空間與 MILP 對等，剩餘差距全記在「貪婪」帳上，不是「解空間被閹割」。

## 5. 拆單的第二個獨立效益：可解性

用固定訂單集（`fixed_fill1350_inv70`，1350 張，4 小時）比較「同一批工作誰做得完」，唯一差別是 `ForbidSplitting`：

| | 每次求解（隨模擬時間） | 待辦訂單 | 結果 |
|---|---|---|---|
| **不拆單** | 1.06 → 8.7 → 10.2 → 31.9 → **151.7 s** | 80 → 118 **單調上升** | **發散，16.4% 時中止** |
| **拆單（正典 M4G）** | 0.312 → 0.224 → 0.188 → **0.151 s** | 87 → 89 震盪穩定 | **9.7 分鐘跑完，1202/1350，零逾期** |

**機制**：「整張單全上或全不上」是離散跳躍，big-M 鬆弛極鬆；拆單把它鬆弛成單位級的連續選擇，線性鬆弛緊得多。

### 救援嘗試

| 手段 | 效果 | 結論 |
|---|---|---|
| **收緊表述**（`TightWholeOrder`）：把 B2 的 big-M + B9 換成每站台等式 `Σ_p qb[o,i,p,s] = d[o,i]·y[o,s]` | 2~3× | **不夠**，25% 時推算仍 612 分鐘、待辦訂單 134 仍在爬 |
| **決定性工作量預算**（`DecisionWorkLimit`，Gurobi `WorkLimit`） | 612 → 82 分鐘 | 有效；未跑完即依使用者指示停止 |

**為何用 `WorkLimit` 而非 `TimeLimit`**：牆鐘上限會讓模擬結果隨機器負載變動，同一份 config 無法重現；工作量上限在任何機器上都在完全相同的搜尋點截斷。兩個旗標都提供，實驗一律用前者。

`HasSolution()` 用 `SolCount > 0` 而非 `IsOptimal()`，且「什麼都不做」永遠可行，所以超限取 incumbent 安全。

## 6. 吞吐量拉不滿：瓶頸不在定價

`MuScale` 掃描（完成訂單獎勵放大）：

| MuScale | 完成訂單 | kJ/訂單 | pile-on | 積壓 |
|---|---|---|---|---|
| M1G 參照 | **656** | 1.9412 | 2.982 | **11** |
| 1（正典） | 608 | 1.1626 | 5.903 | 74 |
| 2 | 607 | **1.1349** | **6.070** | 65 |
| 4 | 619 | 1.1627 | 5.785 | 60 |
| 8 | 619 | 1.1561 | 5.840 | 70 |
| 16 | 616 | 1.1743 | 5.757 | 59 |
| WIP 持有費 | **591** | **1.2431** | 5.472 | 70 |

**獎勵放大 16 倍，訂單數只從 608 到 619 就飽和。** WIP 持有費更糟（591，最低）——罰「開著的單」反而讓模型不敢開單，此方向可放棄。

### 缺口的來源是拆單本身

同一個 M4G 定價，唯一差別是 `ForbidSplitting`：

| | 完成訂單 | kJ/訂單 | 積壓 |
|---|---|---|---|
| M1G 參照 | 656 | 1.9412 | 11 |
| **M4G 不拆單** | **657** | **1.5583** | **11** |
| M4G 拆單 | 608 | 1.1626 | 74 |

μ 加價 16 倍做不到的事，關掉拆單一步到位。缺口完全是 consolidation 尾巴造成的。

### 由此得到的乾淨三分解

| | 完成訂單 | kJ/訂單 | 相對 M1G |
|---|---|---|---|
| M1G（基準） | 656 | 1.9412 | — |
| M4G 不拆單 | 657 | 1.5583 | **能耗 −19.7%，吞吐量持平** |
| M4G 拆單 | 608 | 1.1626 | 能耗再 −25.4%，吞吐量 −7.5% |

**第一段是無可爭議的乾淨勝利**：M4G 的定價機制本身（不含拆單）在完全相同的吞吐量下省 19.7% 能耗。**第二段才是拆單的貢獻，而它有代價**——這是論文該老實呈現的權衡。

## 7. 新增的 gated 旗標一覽

| 旗標 | 預設 | 作用 |
|---|---|---|
| `M4GConfiguration.HonestCompletionReward` | **true** | 修正 §1 的缺陷。false 可重現舊結果 |
| `M4GConfiguration.LineAtomicSplitting` | false | 拆單原子從件收緊到行（§4） |
| `M4GConfiguration.TightWholeOrder` | false | `ForbidSplitting` 的 big-M-free 重寫（§5） |
| `M4GConfiguration.CandidatePodTopK` | 0 | Pa 候選截斷，與 M5 同評分（等策略對照用） |
| `M4GConfiguration.DecisionTimeLimitSec` | −1 | 牆鐘上限（除錯用，非決定性） |
| `M4GConfiguration.DecisionWorkLimit` | −1 | 決定性工作量上限（實驗用） |
| `M4GConfiguration.MipGap` | −1 | 最佳性間隙 |
| `GreedyM5Configuration.CandidatePodTopK` | 0 | 同上，M5 側 |

除 `HonestCompletionReward` 外全部預設關閉；每一個都做過 K=0／關閉狀態的逐位漂移檢查。

## 8. 教訓

1. **漂移檢查只證明「沒污染正典」，完全證明不了新路徑本身是對的。** M4G top-K 第一版通過漂移檢查，但新路徑破壞了「任何通過 PiSKU 過濾的 SKU 必有 ≥1 貨架」的不變式，導致第一次決策就綁 12 張單、派 0 台車、死鎖。gated arm 除漂移檢查外，必須看它自己的輸出合不合理。

2. **不對等策略的比較會製造假發現。** 「貪婪贏過精確」最初是拿 M5(K=10) 比 M4G(K=0) 得到的——兩個不同策略，不是求解品質的比較。

3. **飽和的指標當不了守門員。** items handled 在所有 arm 都是 1430，擋不住任何假性增長。

4. **精確求解器會把目標式的錯誤榨到極致，貪婪不會。** 這使得「啟發式贏過精確模型」成為目標式有缺陷的可靠訊號，而不是啟發式的勝利。
