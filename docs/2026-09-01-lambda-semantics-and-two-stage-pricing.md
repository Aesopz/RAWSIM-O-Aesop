# λ 的語意問題，與兩步定價的失敗

**日期**：2026-09-01
**狀態**：問題已釐清；提出的解法（兩步定價）**實作失敗，記為負結果**
**影響**：決定論文能不能說「λ 是系統當前的最佳兌換率」

---

## 1. 起點：一個看起來像補丁的機制

M4G 的 Dinkelbach 迴圈裡有一段「向上搜尋」：當求解結果退化（P\* ≤ 0）時，把 λ 加倍再解，
最多六次（32 倍）。

```csharp
if (vStar <= 0 && escalations < _m4gConfig.DinkelbachEscalations && lambdaK > 0)
{
    escalations++;
    double lambdaUp = lambdaK * 2.0;
    M4GResult upRes = SolveM4G(model, snap, lambdaUp, ...);
    result = upRes;          // ← 升壓後的方案會被實際採用
    lambdaK = lambdaUp;
    continue;
}
```
（`M4GManager.cs`，`DinkelbachEscalations` 預設 6）

使用者的質疑：**這看起來像補丁，Dinkelbach 沒有標準做法解決這個問題嗎？**

---

## 2. 補丁補的是什麼：前提被違反

教科書 Dinkelbach 求 `min D/P`，前提是**可行集合上每個解都滿足 P(x) > 0**。
在這個前提下：

```
F(λ) = min (D − λP)        凹、對 λ 遞減
F(λ) > 0  ⟺  λ < λ*        ← 「價格太低」的訊號
F(λ) = 0  ⟺  λ = λ*
F(λ) < 0  ⟺  λ > λ*
```

從任何起點都單調收斂，**不需要任何向上搜尋**。

我們違反了這個前提：**空解（什麼都不做）是可行的**，且 D = P = 0、obj = 0。於是

```
F(λ) ≤ 0 恆成立            （空解把 min 壓在 0 以下）
F(λ) = 0  ⟺  λ ≤ λ*        ← 「太低」的訊號永遠是 0，是平的
```

λ 過低時 F 沒有梯度，只能靠加倍去試。**升壓不是 Dinkelbach 的缺陷，是我們把退化解
放進了可行集合的後果。**

---

## 3. 現行 λ 到底是什麼（實測，正典 5 seeds，n = 4735）

### 3.1 迭代停止原因分解

| dinkIters | 決策數 | λ 下調 | λ 上調 | 最終有派車 | \|obj\| ≤ 0.5 |
|---|---:|---:|---:|---:|---:|
| 0 | 1643 (34.7%) | 0 | 0 | 113 | 0 |
| 1 | 2285 (48.3%) | 2285 | 0 | 332 | 25 |
| 2 | 720 (15.2%) | 720 | 0 | 65 | 49 |
| 3 | 10 | 10 | 0 | 4 | 8 |
| 5 | 77 (1.6%) | 0 | 77 | 0 | 77 |

- **λ 曾下調的 3015 次中，最終方案不派車的佔 86.7%**
- λ 完全沒動的 1643 次（34.7%）：D\* = 0，沒有距離樣本可學

### 3.2 「一步」其實就是收斂

原本的判讀是「只走一步、沒收斂」，**這個判讀已撤回**。代數上：

```
空解 obj = 0
某方案優於空解  ⟺  D − λP < 0  ⟺  D/P < λ
⟹ F(λ) = 0  ⟺  不存在比值低於 λ 的方案  ⟺  λ ≤ λ*
```

所以**「收緊後空解變成最佳解」正是 F(λ) = 0，即 Dinkelbach 的收斂條件**。
退化防呆是收斂偵測器，不是失敗。`|obj| ≤ 0.5` 這個測試很少觸發，只因為收斂在這裡
表現成「空解」而非「小目標值」。

### 3.3 λ 的三個候選語意

| | 定義 | 正典數值 | 誰在用 |
|---|---|---:|---|
| 平均已實現率 | `D_cum / L_cum` | λ ≈ 8.0 | λ₀（起點）、靜態臂 |
| 最佳可達比值 | `min D/P` | λ ≈ 3.8 | Dinkelbach 收斂目標 |
| 真正的邊際率 | `∂D/∂P` | **從未量測** | 無 |

現行 λ 每次決策從第一項出發，收斂到第二項，**用完即棄**——下一次決策又從
`D_cum/L_cum` 重新開始。沒有任何機制把歷次的 λ\* 累積起來。

### 3.4 一個曾經誤判的統計

`lambdaEnd` 欄位**會被升壓污染**：

```
B 臂（不拆單）無派車的更新 n=3115   lambdaEnd 中位 409.6  （= 12.66 × 2⁵）
D 臂（正典）  無派車的更新 n=2691   lambdaEnd 中位   3.10
```

那些 400 左右的值是「加倍五次仍找不到正進度方案」的搜尋失敗記錄，不是價格。
**任何從 `lambdaEnd` 算出的價格統計都必須先排除升壓決策。**

（先前一度以為升壓不寫進 `lambdaEnd`，那是看錯欄位——`lambda` 欄不含，`lambdaEnd` 欄含。）

### 3.5 min ≠ mean，不是偏差

只看有距離樣本（`newTrips > 0`）的更新：

| | 真實累積率 | Dinkelbach 取樣均值 | 差 |
|---|---:|---:|---:|
| D 正典 | λ 8.00 → μ 13.02 | λ 3.77 → μ 6.15 | −52.8% |
| B 不拆單 | λ 12.66 → μ 16.72 | λ 8.09 → μ 10.69 | −36.1% |

這個落差**不是估計偏差**：Dinkelbach 求的是 `min D/P`，λ₀ 是 `mean D/P`，
最小值低於平均值是定義使然。物理上它就是 pile-on 的規模經濟——一趟車服務 5.84 張單，
所以「多做一張單」的邊際距離遠低於「平均一張單」。

（先前把它描述成「選擇偏差」，**已撤回**。）

## 4. 提出的解法：兩步定價

把「定價」與「決策」分成兩個問題：

```
第一步（定價）  min D − λP   s.t.  Σ_{p∈Pa} Σ_w z(p,w) ≥ 1
                → 每個解都有 D>0 且 P>0，教科書前提成立
                → 標準 Dinkelbach 從任何起點單調收斂，不需升壓
                → 得到 λ*

第二步（決策）  min D − λ*P   無附加限制
                → 可以自由選擇什麼都不做
```

### 4.1 為什麼約束必須落在「派車」而非「有進度」

若只加 `P ≥ 1`，則「只用沉沒庫存產生進度」的解仍在集合裡，那種解 D = 0、P > 0，
真實兌換率就是 0，λ\* 又退化。**必須約束 `z(p,w)`（強制 D > 0）。**

### 4.2 這不是字典序

先前的字典序方案（`LexicographicRatioFirst`）已於本專案被 5 seeds 否決，兩者不同：

| | 字典序（已否決） | 兩步定價 |
|---|---|---|
| 第二步的可行集 | 被第一步最佳值約束（`obj ≤ obj* + tol`） | 完全不受約束 |
| 兩步的目標式 | 不同（先 D−V，後 min Σu_w） | 同一個 `min D − λP` |
| 第一步的產出 | 一條**限制式** | 一個**參數** λ\* |

第一步的解被完全丟棄，只有純量 λ\* 進入第二步，且作為**係數**而非限制。

## 5. 實作與結果：完全崩潰

### 5.1 實作

- 旗標 `TwoStagePricing`（預設 false）
- `BuildModel(snap, forceDispatch)` 新增限制式 `(FD) Σ_{p∈Pa} Σ_w z(p,w) ≥ 1`
- 第一階段在受限模型上跑 Newton 迭代（**無升壓分支**）求 λ\*
- 第二階段在無限制模型上**只解一次**
- 第一階段的求解時間與迭代次數併入 `solveSec` / `dinkIters`，不隱藏成本

### 5.2 回歸驗證（旗標關閉）

新 binary 跑現行正典，與舊資料 **7/7 指標逐位相同**。改動未污染既有路徑。

### 5.3 兩步定價（2 seeds）

| 指標 | 正典 | 兩步 |
|---|---:|---:|
| 完成件數 | 1428 | **0** |
| 完成訂單 | 596 | **0** |
| 站台到訪 | 101 | **0** |
| 總距離 | 8231 | 896 |
| **決策次數** | **1880** | **72** |
| λ 中位 | 7.98 | **10.00（恆定）** |
| solveSec 中位 | 0.152 s | **2.966 s（慢 19 倍）** |
| 升壓次數 | 34 (1.8%) | 0 |

**零產出。**

### 5.4 崩潰機制

不是預期的「λ\* 太低導致拒絕一切」，而是：

```
第一階段求解極慢（單次 2.97 秒，慢 19 倍）
  → 模擬時間推進被拖垮，2 小時只跑出 72 次決策（正典 1880 次）
  → 沒有產出 ⟹ _closedLines 永不增加
  → InWarmup 恆為真 ⟹ λ 卡在 LambdaFallback = 10.0，從未離開暖機
  → 死鎖
```

慢的原因推測是 `Σ z ≥ 1` 配合 R1/R2/B3 把大量分支變成不可行，求解器必須在一個
**最佳解被切掉**的空間裡找次佳解——那是完全不同難度的問題。

⚠️ 這是推測。診斷不足，因為實作時把兩階段的求解時間合併了。

## 6. 尚未回答的問題

要區分「概念不可行」與「這個實作太慢」，需要把 stage-1 分開記錄：

```
stage-1 是否找到解（HasSolution）
stage-1 算出的 λ*
stage-1 與 stage-2 各自的求解時間
```

改動很小（三個日誌欄位），跑一個 seed 就能判斷。

但即使修好可行性問題，**慢 19 倍本身可能就是致命的**：每次決策多付 2.8 秒，
1880 次決策就是 90 分鐘，這個模型的實用價值即消失。

## 7. 結論與建議

### 7.1 可以寫進論文的

**不能說**：λ 是系統當前的最佳兌換率
→ 只有 3.4% 的決策以容差判定收斂；語意需要更精確的表述

**可以說**：λ 從歷史累積平均 `D_cum/L_cum` 出發，以 Dinkelbach 的 Newton 步
用「上一個解實際達成的比值」把接受門檻往內收；86.7% 的情況下這一步會使原本
看似值得的派車不再划算。

這句話字面準確，且與量測到的效果一致（pile-on +22.9%、EOR −15.1%）。

### 7.2 升壓的處置

- **正典**：升壓消融後七項 KPI **逐位相同**（1.6% 觸發、且從未派車）→ **可以直接移除，零代價**
- **不拆單臂**：移除後件數再掉 3.48%、pile-on 掉 4.59% → **不可移除**
- **統計層**：兩臂都應把升壓決策的 `lambdaEnd` 記為 NA，不納入價格平均

### 7.3 負結果的價值

**把退化解從可行集合移除，在數學上正確，在計算上可能不可行。**

升壓做的其實是同一件事的便宜版本——它不改可行集合，而是調高價格讓非空解自己變得
有吸引力。它確實是補丁，但是一個**保持問題結構不變**的補丁，而結構正是求解速度的來源。
